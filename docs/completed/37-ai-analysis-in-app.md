# 37. AI 약속 만들기 — 분석을 앱에서 직접 수행, 처방전만 OCR 병행

## 무엇을 구현했나
처방전·약봉투 사진에서 약 정보를 뽑아 약속 등록 폼을 채우는 두 화면의 분석 방식 기록.

- `CreatePrescription`(처방전): ML Kit OCR로 텍스트를 뽑고, 이미지와 정렬된 OCR 텍스트를 함께 Gemini(`gemini-2.5-flash`)에 넘겨 파싱.
- `CreatePaperEnvelope`(약봉투): OCR 없이 이미지만 Gemini에 넘겨 파싱. 투약 시간대까지 추출.

## 어떻게 구현했나
- 두 화면 모두 서버를 거치지 않고 앱이 직접 Gemini를 호출한다. 응답은 `parseAndDisplayGeminiResult()`가 파싱해 폼에 채운다.
- 약 이름은 이후 공공 API 조회로 실제 약 정보와 매칭한다(36장).

## 왜 그렇게 판단했나
- **앱에서 직접 호출:** 이 흐름은 사진의 텍스트를 파싱하기만 하면 되고 서버에 저장할 것이 없다. 서버를 거치면 이미지 업로드와 응답 중계 트래픽만 늘어난다.
- **처방전에만 OCR 병행:** 처방전은 OCR 텍스트가 쓸 만해서 이미지와 같이 주면 도움이 된다. 약봉투는 인식이 깔끔하지 않아 OCR로 뽑은 텍스트가 이상했고, 그 텍스트를 줘도 Gemini 단독 결과와 다르지 않았다. 그래서 약봉투는 OCR 단계를 두지 않는다.
  (직접 써 보고 내린 판단이며 정량 비교는 하지 않았다. 모델을 바꾸면 다시 비교해 볼 것.)

## 검토했지만 택하지 않은 대안
- **서버 경유(서버가 Gemini 호출):** API 키를 서버에 두고, 모델 교체·호출 로그·사용량 제한을 한곳에서 할 수 있다. 하지만 저장할 게 없는데 이미지 업로드와 중계 트래픽만 늘어서 택하지 않았다.
- **약봉투에도 OCR 병행:** 처방전과 코드를 맞출 수 있지만 위 이유로 결과가 나아지지 않아 택하지 않았다.

## 남은 것
- 앱 쪽 호출에서 API 키가 어떻게 보호되는지(Firebase 경유 여부)는 이 문서 작성 시 코드로 확인하지 못했다.
